# BLINKA — L1 v3.0 Financial Evidence Intelligence

**Status:** DESIGN FROZEN (architecture + interfaces); implementation and empirical verification pending.  
**Supersedes:** L1 v2.0.  
**Decision:** ADR-003 amendment v3.0, 2026-10-17.  
**Consumer boundary:** L2 Financial Decision Kernel, governed by L3 AP Harness.  
**Scope:** Hackathon scenario, exclusively synthetic documents. No real banking or payment operations.

## 1. Mission and safety boundary

Produce reproducible, source-attributed financial facts from PDF, image, email and chat, including a claim about their mechanical verifiability. L1 **never authorizes** payments, matches against an authoritative contract, consumes budget, approves a beneficiary, performs identity/fraud/compliance checks, or grants agent capabilities.

L1 claims are still untrusted until accepted by a trusted verifier; `OBSERVED` is not `VERIFIED`. An `ACCEPTED` report is scoped to structure, provenance and tested consistency, not perfect optical recognition or ultimate business truth. Ambiguous material values are never silently guessed.

L3 owns runtime scheduling, agent capability grants, Evidence Admission Gate, remediation assignments and HITL. L2 independently checks that a report was created by a trusted verifier, is bound to the exact invoice and source digests, is current according to its own policy, and that all financial policy gates pass. L1 status alone is never authorization.

## 2. Frozen functional components

1. **Multichannel Intake & Source Registry.** Register the original bytes or immutable message snapshot; tenant-scope; SHA-256; store in controlled durable storage. Deduplicate identical uploads for processing (NOT business invoice duplicate determination).
2. **Adaptive Parsing.** Direct text for native email/chat; LiteParse preferred for digital PDFs; LlamaParse preferred for complex scans and images. Route based on document properties and confidence in the native text layer, not solely format extension.
3. **Optional Classification / Splitting.** DocJev candidate for heterogeneous packets only; bypass for known single invoices. Preserve original page mapping, classify uncertain packets as review required.
4. **Structured Invoice Extraction.** LlamaExtract preferred; map vendor output to stable `InvoicePayload`, explicit missing/ambiguous/conflicting fields and field evidence claims. Do not allow provider-specific types outside the adapter.
5. **Deterministic Verification & Normalization.** Validate TypeScript runtime schema (Zod planned); bind spans to the immutable source or retained parse artifact; check mathematical consistency; derive a candidate payable amount and USD equivalent with decimal arithmetic; emit trusted `VerificationReport` and `InvoiceEnvelope`.

No vector DB or generic RAG is required in L1. Retrieval of contracts belongs in the L3-governed Reconciliation workflow, while authoritative matching and policy decisions belong to L2.

## 3. Stack and implementation disposition

- TypeScript strict + Node.js for orchestration contracts; Hono API adapter recommended.
- LiteParse Node binding preferred local digital PDF parser; LlamaParse managed service as complex-doc fallback.
- DocJev remains optional (Python and hosted Jev add integration complexity).
- LlamaExtract managed service preferred for structured extraction and citation proposals.
- Zod for runtime validation; decimal.js for base-10 amounts and FX. Versions and provider-specific request/response shapes must be pinned and proven during implementation.
- Artifact persistence: implementation choice open. Must preserve immutable original and selected parse/extraction/verification snapshots independently from cloud provider retention.
- Vitest with isolated, offline deterministic tests; live provider contract tests separate.

## 4. Contract definitions (locked)

Canonical types in [`../contracts/l1.contracts.ts`](../contracts/l1.contracts.ts):

- `DocumentSource`: tenant, source channel, digest, immutable artifact locator, type and ingest time.
- `DocumentSegment`: page-contiguous source mapping for split packets (optional).
- `EvidenceReference`: citation id, original source and digest, optional segment, normalized page box or UTF-8 byte ranges, quote and proposer.
- `ObservedField<T>`: `OBSERVED` (with evidence), `MISSING`, `AMBIGUOUS` or `CONFLICTING`; no source-less auto-filled amounts.
- `InvoicePayload`: separate invoice ID and dates, billing period, legal beneficiary, tax ID, bank/wallet account, commercial references and line items, source-observed monetary components.
- `FxRateSnapshot`: immutable, configurable quote-per-USD rate for the source currency, effective time, rounding, source and ID (demo must support COP and MXN).
- `FinancialNormalization`: source-to-candidate-payable derivation, method, traced operands and optional USD equivalent. Only supported/certain values yield a candidate.
- `VerificationCheck` and `VerificationReport`: machine-readable evaluation with trace and trusted issuer boundary.
- `InvoiceEnvelope`: discriminated successful/failed result, schemaVersion, immutable provenance, source artifacts and processing errors.
- `L1EvaluationSuite`: input fixtures, human ground truth and release guards.

**Version:** `3.0.0`. Breaking changes to these interfaces require a new contract major version and migration strategy; nonbreaking optional metadata may be added in minor versions. `schemaVersion` is checked at all downstream boundaries.

## 5. Normative invariants

1. All external documents and LLM output are treated as untrusted data. Invoice text must never override instructions, capabilities or policies.
2. `READY_FOR_POLICY_EVALUATION` requires a trusted `ACCEPTED` verification report, digest-bound to exactly the source and normalized invoice in the envelope, with no failed critical check.
3. Missing, conflicting or uncertain **critical payable amount, currency or beneficiary evidence** forces non-ready status. Other fields have field-specific requirements defined by the versioned verification rules and downstream policy.
4. Numeric amounts are canonical decimal strings; no `Number` floating-point arithmetic is used for monetary decisions. Preserve original amount; record every conversion parameter and rounding rule.
5. Document-observed and calculated values must never be conflated. The USD amount is computed by code, never accepted from LLM arithmetic.
6. FX uses a **configured, versioned rate per non-USD source currency**: `sourceAmount / quotePerBase = USD`, rounded HALF_EVEN to 2 decimals, where `1 USD = quotePerBase units of sourceCurrency`. Demo configurations MUST support COP and MXN; USD uses identity. Unknown currencies, absent rates, zero/negative rates, or currency-pair mismatches result in REVIEW_REQUIRED.
7. Every observed critical field points to a unique, stored evidence reference; verifier checks the existence, referential integrity, span/region validity and available text matching. OCR text matching alone does not prove visual correctness.
8. Source digests, normalized payload digests, parser/extractor versions and artifacts are retained for replay; replay of deterministic verification/calculation is expected, not byte-identical re-generation by an LLM.
9. Failed/uncertain invoices remain auditable. They must not be discarded before the L2/L3 safe-outcome path records their status; infrastructure failure is not mislabeled as a business authorization.
10. One source may contain multiple invoice segments, each with its own envelope and references to the original source. Any uncertain split demands review.
11. L1 never issues `PAID`, `AUTHORIZED_SIMULATED`, `BLOCKED`, payment instructions or human approvals. These belong to L2/L3.
12. Sensitive account identifiers remain access-controlled; public explanations use redacted identifiers and stable keyed fingerprints rather than raw account numbers.

## 6. Source-aware evidence assurance

**Source integrity:** SHA-256, immutable copy, artifact checksums and tenant access boundaries.  
**Grounding:** page number and normalized bbox in original source, or exact UTF-8 byte range in an immutable text representation; quote matching is checked where possible.  
**Consistency:** supported numeric relationships, currency agreement, date format/ranges, line totals when all operands are present.  
**Uncertainty:** no fake citations, no assuming perfect OCR. A fuzzy match or visual ambiguity moves a critical field into review.  
**Trust:** verifier's issuer integrity is enforced at infrastructure/read-boundary level (trusted storage/service authentication), not by a model choosing `status: ACCEPTED`.

For native text spans, use UTF-8 bytes, not JavaScript UTF-16 string indices; for page boxes use normalized 0..1 coordinates and retain original page dimensions in referenced artifacts for rendering.

## 7. Canonical flow

`Intake → Source Registry → Route → (Direct text | LiteParse | LlamaParse) → (optional DocJev) → Extract → Ground → Normalize → Verify → InvoiceEnvelope`

- Ready: send envelope through L3 admission to L2 independent policy evaluation.
- Review/rejected: preserve envelope for financial audit and L3 remediation; L2 must never autoauthorize.
- Provider failure: persist processing incident; orchestrator retries within bounded policy; not a business/payment decision.

## 8. Contract examples and error handling

- Missing invoice number on a Colombian `cuenta de cobro` is explicitly `MISSING`. L2 may block/escalate depending on policy, never fabricate a number.
- Invoice text with both USD 2,500 and USD 2,850 totals uses `CONFLICTING` or `AMBIGUOUS` with evidence-backed candidates; no arbitrary winner.
- A source that says `Invoice Total 2,850; Paid 0; Due 2,850` yields a candidate payable from source-backed outstanding balance if arithmetic passes; if a partial payment is claimed but the remaining balance is unclear, no candidate is emitted.
- A PDF pretending to tell agents to 'ignore approvals' is ordinary untrusted document text, never instructions.
- An OCR digit error that cannot be resolved by textual grounding requires review rather than pretending the verification result proves the image.

## 9. Evaluation contract and acceptance

The release corpus starts with **at least 30 fully synthetic labeled samples** (including the v3 MXN cases), including SaaS USD PDF, Colombian COP/USD cuentas de cobro, photographed invoices, email and chat text, mixed PDFs, misleading totals, duplicates, beneficiaries with changed bank accounts, unreadable fields, and prompt injection. A separate deterministic test suite validates the verifier, numeric conversion, source hash and envelope invariants without calling providers.

Release gating for this fixture set (not a population-wide guarantee):
- `0` cases of unsafe `READY_FOR_POLICY_EVALUATION` on deliberately corrupted critical data.
- `0` cases of accepted critical observed fields with missing/invalid evidence.
- `0` failed deterministic FX/rounding test vectors.
- All source hashes and provider/version metadata preserved on processing results.
- Failures and uncertain outcomes always persisted with explicit reasons.
- Live smoke tests of at least one digital PDF, one COP cuenta de cobro and one scan, comparing normalized fields against human ground truth.

Measure exact critical-field match, citation support, false verification, appropriate escalation, end-to-end p50/p95 and per-invoice cost, but do not make unmeasured accuracy claims.

## 10. Go / No-Go and boundary commitment

**GO for L2 architecture:** immediately, against the L1 v3.0 contract.  
**GO for Codex implementation:** the interface is specified; providers, schemas, storage and integration must be validated while coding.  
**NO-GO for describing L1 as production-verified:** until tests and external adapters pass on representative documents.

The harness governs the *admission and use* of evidence; it never redefines the invoice schema or impersonates the trusted verifier. Financial authorization remains entirely with L2.


## 11. v3.0 contract amendment — multi-currency normalization

- Breaking interface revision: `L1_CONTRACT_VERSION = '3.0.0'`; readers must reject unknown major versions and migrate v2 snapshots explicitly. Do not silently relabel persisted v2 envelopes as v3.
- `FxRateSnapshot.quoteCurrency` is an ISO 4217 `CurrencyCode`, rather than the literal `COP`. For the demo, both `USD/COP=4000.00` and `USD/MXN=20.00` are fixed synthetic rates (NOT market rates), with rate IDs and timestamps.
- `FinancialNormalization.method = DIVIDE_BY_USD_QUOTE_RATE` generalizes the v2 COP-only method. Positive finite DecimalStrings only, matching invoice currency and configured rate currency; HALF_EVEN to 2 decimal USD scale; no JavaScript floating point.
- USD amounts use `USD_IDENTITY`, with `fx: null`, avoiding fictional USD/USD quotes. Rate absence, mismatch, invalid rate or unknown currency must not yield `READY_FOR_POLICY_EVALUATION`.
- Report currency conversion provenance in the trace and preserve source financial values unmodified. Both extraction and normalization failures remain auditable.

## 12. v3.0 integration: multi-source Accounts Payable cases

L1 processes each `DocumentSource` independently, even when multiple sources are part of one payable case. Its output includes the unchanged source ID and hash. **L3** is solely responsible for constructing the `PayableCase` that correlates, for example, an Argentina contractor's invoice PDF with a supporting chat message. A supplemental chat message need not itself produce an `InvoiceEnvelope` if it is not an invoice; its immutable original source is still retained and can be linked by L3 as contextual evidence. L3 MUST verify the association rather than join documents merely because filenames or free-text names resemble each other. No citation may claim to belong to another source.

L2 compares the extracted factual claims with the authoritative vendor directory, active agreements, ledger and budget. Source registration and document-level matching are not accounts-payable duplicate detection.
